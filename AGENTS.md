# London Rent

A small prototype for exploring London neighbourhoods when looking for a flat to rent. Agents collect raw data, one command turns it into a single JSON file, and a static page shows it on a map.

```
fetch (agents / scripts)  ->  data/*  ->  npm run reindex  ->  data.json  ->  index.html
```

## Layout

```
index.html        the whole frontend: markup, CSS, JS and the category config
data.json         GENERATED by reindex, the only file the frontend loads
data/             raw fetched artifacts, flat, plus index.json describing them
scripts/fetch/    one self-contained script per fetchable source
scripts/reindex.mjs   data/ -> data.json
```

The repo root is the app root.

## Commands

- `npm run fetch` runs every fetch script (`npm run fetch:supermarkets`, `npm run fetch:osm-places`, `npm run fetch:parks`, `npm run fetch:tfl`, `npm run fetch:boundaries`, `npm run fetch:crime`, `npm run fetch:tenure`, `npm run fetch:rents` individually)
- `npm run reindex` rebuilds `data.json` from `data/`
- `npm run serve` serves the app at http://localhost:3000 (the page needs HTTP, `file://` will not work)

## The data folder

- Flat: no subfolders.
- Raw: files are saved exactly as the source returned them, JSON or CSV. Never hand-edit a fetched file; fix the fetch or the adapter instead.
- Named in kebab-case, prefixed by source: `osm-supermarkets-london.json`, `tfl-line-victoria.json`.
- Every file must have an entry in `data/index.json`. `npm run reindex` fails if a file is not indexed or an indexed file is missing.
- Re-fetching overwrites the file and updates `fetched_at` in its entry.

### data/index.json

An array with one entry per raw file:

| field | meaning |
| --- | --- |
| `file` | file name inside `data/` |
| `title` | what the file contains |
| `source` | where it came from (API, website, person) |
| `url` | endpoint or page it was fetched from |
| `query` | optional, the query sent (e.g. Overpass QL) |
| `fetched_at` | ISO timestamp of the fetch |
| `method` | `script` or `manual` |
| `script` | for `method: script`, the script that produces the file |
| `format` | short description of the file's structure |
| `adapter` | which adapter in `scripts/reindex.mjs` reads it |

## Adding a data source

1. Get the raw data into `data/`.
   - If there is an API, write a self-contained script in `scripts/fetch/` that saves the response and upserts its own index entry (copy `scripts/fetch/supermarkets.mjs`), and add it to `package.json`.
   - Otherwise fetch it by any means (browser, manual lookup), save the file and write the index entry by hand with `method: "manual"` and honest provenance in `source` and `url`.
2. Point the entry's `adapter` at an existing adapter in `scripts/reindex.mjs`, or add a new adapter function there if the format is new.
3. Run `npm run reindex`.
4. Separately, if the new points should show up as their own group, add a category in `index.html`.

## data.json

Generated, never edited by hand. Facts only:

```json
{
  "generated_at": "ISO timestamp",
  "points": [{ "id": "", "dataset": "", "name": "", "lat": 0, "lon": 0, "props": {} }],
  "lines":  [{ "id": "", "dataset": "", "name": "", "mode": "", "paths": [[[lat, lon]]], "routes": [["station id"]] }],
  "areas":  [{ "id": "", "dataset": "", "name": "", "lat": 0, "lon": 0, "polygons": [[[[lat, lon]]]], "props": {} }]
}
```

Areas are wards and boroughs, with the ONS code as `id`, and parks, with the OSM element as `id`. Files that describe areas rather than draw them (crime counts, tenure, rents) are joined onto the area with the same code as `props.crime`, `props.tenure` and `props.rent`.

`dataset` says which source a feature came from. `props` carries source facts such as `brand`, `address`, `zone`, `lines`.

## Categories are a runtime concern

Categories, icons, colours and rail line styles live only in the CONFIG block at the top of the script in `index.html`. A category is a label, an icon, a colour and a `match(point)` predicate; a point belongs to the first category that matches.

Fetch scripts, `data/index.json`, adapters and `data.json` must never mention a category, icon or colour. Regrouping or restyling must be possible by editing the config block and reloading the page, with no re-fetch and no reindex.

## Code style

This is a prototype. Keep it simple.

- Frontend: vanilla JS, HTML and CSS in the single `index.html`. No build step, no framework, no extra files. Leaflet from a CDN is the only library.
- Write linear, top-to-bottom code. Do not extract functions, helpers or modules until something is duplicated three times.
- Scripts: Node 24, ESM, no npm dependencies.
- Be polite to public APIs: set a User-Agent, make requests sequentially.

## What goes on the map

- Supermarkets: full-size stores only, no convenience formats (Tesco Express, Sainsbury's Local, Little Waitrose, corner shops). The chain list and the exclusions live in `scripts/fetch/supermarkets.mjs`; to add a chain, extend `chains` there, re-fetch, reindex, then add a category in `index.html`.
- Climbing gyms: drawn as points.
- Hipster pockets: semi-transparent zones where independent "taste" places cluster. Inputs are speciality coffee shops, climbing gyms, yoga and pilates studios, craft breweries, record shops, vintage clothing and independent bookshops, fetched by `scripts/fetch/osm-places.mjs` (one raw file per kind, the OSM filters live there). Apart from climbing gyms these places are not drawn as points. The scoring (grid size, radius, weights, thresholds) lives in the `zone` config in `index.html` and is computed in the browser, so it can be tuned with a reload. Coffee is a curated list on purpose (`data/ect-cafes-london.json`, European Coffee Trip, saved manually from the page because the site blocks scripts); OSM cafes are too noisy to tell third-wave places from the rest.
- Rent: not drawn. ONS average monthly rents per borough are still fetched by `scripts/fetch/ons-rents.mjs` (one raw file per borough, about 21 MB in total because each also carries house price history) and sit in `data.json` as `props.rent` on the borough areas. Borough is the finest level ONS publishes, which proved too coarse to be useful as labels on the map.
- No-go wards ("Unsafe streets"): the couple of dozen outlier wards for walking home alone at night, shaded dark, everything else left clear. A ward is drawn when its score is at least `crime.times` (4) times the median London ward's. The source is Met Police recorded crime per ward, fetched by `scripts/fetch/met-crime.mjs`; `data.json` keeps the 12 month total of every crime kind per ward. The score lives in the `crime` config in `index.html` and is computed in the browser: a weighted sum per km² of street crime (muggings and sexual offences count double; violence with injury, weapons, drug dealing; threatening behaviour and drug possession at half), discounted by the share of the ward's crime that is shop and crowd theft, so busy centres do not light up just for being busy. Phone snatching and pickpocketing count only beyond 20 times the median ward's density. Burglary, vehicle crime, violence without injury, stalking and rape are left out as mostly not about walking the streets (the reasons are in the config comment). The City of London has its own force and is never shaded. Retired ward codes in the Met file match no boundary and are dropped by reindex with a warning.
- Social housing: wards where at least `social.min` (40%) of households rent from the council or a housing association are outlined in purple, over the crime shading, and the crime tooltip gives the share. The source is Census 2021 tenure (TS054) per 2022 ward from Nomis, fetched by `scripts/fetch/census-tenure.mjs` and kept as `props.tenure` (`households`, `social_rented`). The 2022 wards match the 2024 boundaries everywhere except the City of London, which has no figures.
- Duplicate OSM points: one place is sometimes mapped as several nodes (Canary Wall has one per railway arch), so the `osm-pois` adapter keeps only the first point of a dataset with the same name within about 100 m.
- Parks: a faint green, with no hover, because the basemap is greyed out and its own parks barely show. Outlines of parks, commons and nature reserves come from OpenStreetMap, fetched by `scripts/fetch/osm-parks.mjs` (private ones are left out); reindex joins the pieces of the big ones into rings, ignores holes such as lakes and keeps the size as `props.area_km2`. The colour, opacity and the smallest park drawn (`minHa`, 1 hectare) live in the `parks` config in `index.html`.
- Travel times: hovering a station shows the estimated minutes to each office. Nothing is fetched for this: it is the quickest path over the rail lines, computed in the browser from the station order in `routes` on each line (one list of station ids per branch). Speeds, minutes per stop, the cost of boarding or changing and the walking limits live in the `commute` config in `index.html`. It was tuned against the TfL Journey Planner at 08:30 and is typically within 3 minutes of it, but it knows no buses or National Rail, so stations with a fast mainline train come out too slow. Asking the planner for every station and office takes about 850 requests, half an hour and 80 MB of responses, which is why it is an estimate.
- Ward and borough boundaries come from `scripts/fetch/ons-boundaries.mjs`.

## Git and deploy

- Work on `main` and push straight to `main`. Do not create branches or pull requests.
- The site is deployed by GitHub Pages from the root of `main`, so pushing to `main` is the deploy. There is no build step. It is live at https://vadik49b.github.io/london-rent-what-i-like/ a minute or so after the push.
- `data.json` is committed, so run `npm run reindex` before pushing whenever `data/` changed.
